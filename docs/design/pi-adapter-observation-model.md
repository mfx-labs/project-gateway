# Pi Adapter Observation Model (WP-5A)

**Status:** Normative WP-5A design
**Module:** `src/adapters/pi/observation.ts`

## Purpose

`PiExecutionObservation` is an immutable, runtime-branded adapter record of
what the Pi host reported during one observed execution of a projected plan. It
is correlation and observation data only.

## Session and Turn Correlation

- `sessionCorrelationId` is captured from the host session manager at
  `session_start` (read-only `ctx.sessionManager.getSessionId()`).
- `turnCorrelationId` is derived from the host `turn_start.turnIndex`.
- `occurrenceId` and `attemptId` come from the plan (caller-supplied identity,
  never generated by the adapter) and are preserved verbatim.
- A `session_start` with a non-startup reason produces a stable
  `PI-ADAPTER-CORRELATION-MISMATCH` finding.

## Completion Observations

- Assistant text is captured from `message_end` assistant messages.
- `completionStatus` is one of `completed`, `cancelled`, `error`,
  `not-observed`, derived from observed events:
  - host cancellation observation → `cancelled`;
  - observed host tool errors → `error`;
  - assistant completion text → `completed`;
  - otherwise `not-observed`.
- `completeness` is `complete` (completion + shutdown observed), `partial`, or
  `cancelled`.

## Tool-Call Observations

- `tool_execution_start` / `tool_execution_end` / `tool_call` events are
  captured as data with stable sequence numbers (host order).
- The bridge never blocks, mutates, enables, or disables a tool; `tool_call`
  handlers return `undefined`.
- `toolObservationImpliesPermission` is always `false`.

## Cancellation and Errors

- Pi 0.83.0 has no distinct public cancellation extension event; cancellation
  is recorded only from a host-supplied cancellation observation
  (`bridge.recordCancellation()` or `observe({ cancelled: true })`).
- Host error observations (e.g., `tool_execution_end` with `isError`) are
  listed as `hostErrors` with stable entries.

## Untrusted Host Timestamps

In the verified Pi 0.83.0 public lane, `turn_start` carries a `timestamp`
field; completion, settle (`agent_settled`), and shutdown (`session_shutdown`)
events generally do **not** supply public timestamps. The adapter records an
event timestamp only when the host actually supplies one (defensive capture),
never synthesizes trusted timestamps, and never uses a `Date.now()` fallback
for protocol or observation authority. Missing end timestamps are expected on
this supported lane and are simply absent from the observation.

## Distinction from ExecutionResult and TrustedReceipt

Every observation explicitly states:

- `isAdapterObservation: true`;
- `isExecutionResult: false` — Pi completion output is not an ExecutionResult
  until a later trusted evaluator produces one under the approved lifecycle
  protocol;
- `isTrustedReceipt: false` — Pi output is never a TrustedReceipt;
- `impliesAuthorization: false` — observation is not proof of authorization;
- `toolObservationImpliesPermission: false` — observed tool calls were not
  authorized by this adapter.

The adapter creates no lifecycle records and persists nothing.
