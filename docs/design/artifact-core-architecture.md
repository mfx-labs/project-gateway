# Artifact Core Library Architecture

**Status:** Normative WP-4 design
**Package:** `@project-gateway/artifact-core` (private, v0.1.0)
**Applies to:** `src/**`

## Purpose and Trust Boundary

The Artifact Core Library is a consumer-neutral, deterministic validation and
protocol-evaluation library that realizes the approved WP-0 through WP-3 artifact
protocol. It is not an MCP server, workspace service, artifact store, lifecycle
database, approval authority, execution controller, Pi adapter, pi-guard adapter,
completion evaluator, CLI, or network service.

The core performs no hidden I/O. It never reads arbitrary files, traverses
directories, accesses Git, invokes processes, uses shell commands, makes network
requests, accesses environment secrets, stores lifecycle state, allocates
approvals or issuances, activates executions, starts Pi, modifies artifacts,
rewrites invalid input, depends on the current working directory, or reads the
wall clock. All external state arrives through explicit interfaces:

- raw input bytes/strings (caller-supplied);
- the packaged schema catalog and conformance corpus (embedded at build time);
- identity state (injected `IdentityStateView`);
- exact-subject resolution (injected `ExactSubjectResolver`);
- accepted registry context and consumer support (injected);
- lifecycle records (injected as data);
- current time (injected per call).

## Module Boundaries

| Module | Responsibility |
| --- | --- |
| `src/json/` | Raw JSON intake: UTF-8 decoding, byte bounds, nesting bounds, duplicate-member rejection before object construction, malformed-JSON and Unicode rejection, source-location tracking, construction of one accepted model. |
| `src/canonical/` | Canonical-input validation (NFC, safe integers, timestamps, bounds) and RFC 8785 (JCS) serialization. Never normalizes, sorts, clamps, or discards data. |
| `src/digest/` | Artifact and RegistrySnapshot canonical projections, domain-separated SHA-256 digests, and digest verification. |
| `src/schema/` | Offline schema catalog registry (`$id`-keyed), Draft 2020-12 compilation, and schema identification from approved discriminators. |
| `src/identity/` | Identity/lineage validation over the injected identity-state view; `MemoryIdentityState` for tests and the conformance runner only (no persistence). |
| `src/references/` | Exact-reference validation: resolver output is treated as untrusted and revalidated; every reference field is compared; no path/alias/latest/partial/fallback resolution exists. |
| `src/registry/` | RegistrySnapshot semantic evaluation and artifact/consumer registry compatibility against the accepted snapshot. |
| `src/semantic/` | The 114-rule semantic catalog with stable rule IDs; structurally enforced rules are registered and satisfied at the structural phase. |
| `src/bundle/` | Bundle and cross-artifact workspace/lineage compatibility (evaluation only). |
| `src/lifecycle/` | Trusted lifecycle graph validation and registry-context evaluation over caller-supplied records. |
| `src/pointofuse/` | Point-of-use eligibility with injected time, ceilings, support, and revocations. |
| `src/engine/` | The ordered phase pipeline for artifact revisions, registry snapshots, and lifecycle records. |
| `src/conformance/` | The manifest-driven conformance runner over the embedded WP-3 corpus. |
| `src/api/` | The stable public API surface. |
| `src/generated/` | Deterministic build-time mirrors of `schemas/**` and `fixtures/**` (regenerated by `scripts/generate-bundle.mjs`; never edited by hand). |

## Complete Effective-Authority Flow

Point-of-use evaluation MUST begin from an exact verified `ExecutionBundle` and
its exact trusted lifecycle chain:

- the exact bundle and its four prospective member artifacts (`TaskSpec`,
  `AuthorityPolicy`, `ContextManifest`, `CompletionContract`) are resolved and
  revalidated as untrusted input (raw/canonical/structural/digest/existing
  identity registration/lineage/semantic/registry/consumer support), and every
  member reference field (protocol, kind, kind version, instance ID, revision
  ID, digest, workspace binding) is verified;
- only lifecycle records related to the exact bundle revision, the exact four
  referenced artifact revisions, the exact accepted registry context, the exact
  `RuntimeGrant`, and the exact requested workspace are evaluated — an
  unrelated lifecycle record never affects the result;
- the required lifecycle chain (validation, approval, issuance, grant, and
  activation or pre-activation state required by the requested operation) is
  mandatory: missing required lifecycle state and a missing `RuntimeGrant` fail
  closed;
- revocations apply only to related revocable records (`ApprovalRecord`,
  `IssuanceRecord`, `RuntimeGrant`, `ResultPublicationRecord` when relevant);
  historical fact records are never revocable;
- every applicable `RuntimeGrant` `narrowed_constraint` is enforced (a
  read-only grant never authorizes a write request);
- the exact requested operation (capability, operation class, resource class,
  scope, limits) is evaluated as the intersection of the global capability
  ceiling, the workspace capability ceiling, the approved `AuthorityPolicy`
  (deny wins; unknown capability, operation, scope, selector, or required
  semantic is denied), the active `RuntimeGrant` (validity, revocation, attempt
  allowance, narrowed constraints), and consumer support, with registry
  compatibility (exact accepted snapshot, registered extensions, supported
  features and capabilities);
- findings are sorted deterministically before the first failing phase is
  chosen, so the first reported phase is the earliest actual failure.

The requested workspace must match the bundle, policy, context, grant,
lifecycle-record, and consumer-use workspaces. Portable `TaskSpec` and
`CompletionContract` use remains workspace-scoped through lifecycle records.
Effective-authority evaluation never creates approval, issuance, grant,
activation, use counts, or persisted state, and never starts execution. Time is
always caller-supplied.

## Phase-Gated Pipeline and Identity Modes

The artifact pipeline stops exactly at the requested `through` phase:
`canonical-input-validation`, `schema-identification` (marked
`canonical-input-valid`), `structural-schema-validation`
(`structural-valid`), `canonicalization-and-digest-verification`
(`digest-verified`), `identity-registration` (proposed-registration checks
only; never mutates identity state), `semantic-self-validation`
(`self-semantic-valid`), and `registry-compatibility`
(`registry-compatible` — assigned only after actual registry and
consumer-support evaluation succeeds; missing registry inputs fail closed).
Later lifecycle and point-of-use levels are assigned only after those phases
execute in their own entry points.

Identity execution at phase 6 has two distinct modes that are never mixed:
`checkProposedRegistration` (instance reuse, revision reuse, digest conflicts,
predecessor conflicts, generation conflicts — used only when the
`identity-registration` phase is explicitly requested) and
`verifyExistingRegistration` (instance exists, revision exists, revision
belongs to the instance, registered digest/generation/predecessor/workspace
binding match — used by for-use validation, which never runs
proposed-registration checks and never rejects a valid already-registered
genesis revision as new instance reuse).

## Deep Immutable Snapshot and Private Membership Branding

Validated wrappers own a defensive deep snapshot of the accepted JSON data
model: only plain JSON value types are copied via own data-property
descriptors; caller prototypes, getters, setters, methods, symbols, inherited
properties, custom classes, and proxies are never preserved; accessors are
never invoked; every array and object is deeply frozen (null-prototype
objects), so prototype pollution is invisible to validated models. No nested
reference is shared with caller input.

Snapshot traversal state is strictly per top-level `snapshotJson()` call: the
recursion stack distinguishes true cycles from repeated acyclic shared
references (which are accepted and materialized as independent immutable JSON
subtrees), cleanup uses `try/finally`, and a failed nested traversal can never
contaminate later calls, other inputs, other library instances, or concurrent
or reentrant calls. No module-global traversal state exists.

Runtime branding uses module-private `WeakSet` membership with public type
guards: no brand is stored as an own symbol property, string property,
exported token, or global symbol, so `Object.getOwnPropertySymbols(wrapper)`
reveals nothing and a spread, clone, proxy, or forged lookalike is never a
member. Artifact, registry-snapshot, and lifecycle-record memberships are
distinct, and membership is valid only within the physical module instance
that created the wrapper. Brands distinguish validated artifacts, registry
snapshots, and lifecycle records, and each wrapper records its explicit
validation level.

## Explicit Validation Levels

Validation levels are explicit and recorded on every wrapper
(`raw-parsed` → `point-of-use-eligible`). `validateArtifactSelf` stops at
semantic self-validation; `validateArtifactRevision` requires an explicit
`through` phase and stops exactly there; `validateArtifactForUse` requires
registry, consumer support, resolver, identity, lifecycle, revocation, and
point-of-use inputs, uses them all, and fails closed when required
dependencies or required lifecycle state (including the `RuntimeGrant`) are
missing. A self-validated subject is never accepted where a for-use validated
subject is required (`isLevelAtLeast`).

## Exact-Reference Self versus For-Use Resolution

References are validated against the approved Draft 2020-12 exact-reference
schema (unknown members rejected). Self resolution (`validateReferenceModel`)
revalidates the resolver output through raw parsing, canonical input, schema
selection, structural schema, canonicalization and digest, existing identity
registration, lineage, and semantic self-validation, then compares every
reference field independently; it never claims registry compatibility. For-use
resolution (`validateReferenceModelForUse`) additionally requires the accepted
registry context and consumer support and revalidates the target through
registry compatibility before any field comparison; `registry-compatible` is
returned only after actual registry evaluation, absent required inputs fail
closed, unsupported required extensions and features are denied, and
workspace bindings are compared semantically and insertion-order
independently. No `skipIdentity` path bypasses verification.

## Oracle-Independent Conformance Execution

The conformance runner produces actual findings from implementation-owned
logic: rule IDs come from evaluators, the structural-enforcement mapping
(schema resource + validator keyword + path), graph evaluation, or raw/
canonical phases — never from the manifest. Schema-resource (`SCH-*`) fixtures
resolve their execution target from an implementation-owned fixture-path→
catalog mapping (disambiguated by subject-type label for the two shared
fixture paths), never from `expected_schema_id`, and canonical-vector entries
produce an actual evaluation object (success/failure, phase, category, rule
IDs, canonical projection, canonical UTF-8, digest, rejection reason) that is
routed through the same comparison logic as other entries. Expected values are
read only for comparison after execution; altering an expected value (schema
ID, rule ID, category, phase, pass/fail, digest) produces a mismatch.

## Deterministic Data Flow

```
raw bytes ──► json/scanner ──► canonical/input ──► schema/select ──► schema/registry
                (phase 1)         (phase 2)          (phase 3)         (phase 4)
                                                                          │
          digest/artifact ◄── canonical/jcs ◄── canonical set ordering (phase 5)
                                                                          │
          identity/validate (phase 6) ──► semantic/engine (phase 7)
                                                                          │
          references/validate (phase 8) ──► bundle/validate (phase 9)
                                                                          │
          registry/evaluate (phase 10) ──► lifecycle/graph (phase 11)
                                                                          │
          pointofuse/evaluate (phase 13)
```

Every phase returns deterministic findings through the shared report model; the
first failing phase prevents all later authority-dependent use.

## Dependency Injection

- `IdentityStateView` — registrar view (instance/revision registration, digest
  binding, predecessor lookup). WP-4 provides no persistent implementation.
- `ExactSubjectResolver` — returns the referenced subject; the core revalidates
  the returned value through the full pipeline before comparing any field.
- `AcceptedRegistryContext` + `ConsumerSupportDeclaration` — trusted configuration.
- Lifecycle records, revocations, ceilings, and current time — supplied per call.

## No-I/O Core Policy

Production modules import only Node built-ins (`node:crypto`) plus the embedded
generated bundles. The security test suite scans the compiled output for
`node:fs`, `node:net`, `node:http`, `node:https`, `node:child_process`, `fetch`,
`process.env`, and `Date.now` and fails if any appears in protocol code.

## Protocol Equality (W4-F1)

JSON object member insertion order is not semantically significant. All
workspace-binding, exact-reference, and bundle-reference equality decisions use
explicit protocol-semantic comparators owned by one consumer-neutral internal
module (`src/internal/protocol-equality.ts`): `workspaceBindingsEqual`
(portable/bound mode, exact workspace ID), `exactReferencesEqual` (protocol
version, artifact kind, kind version, instance ID, revision ID, canonical
digest, workspace binding), and `bundleReferencesEqual` (the exact-reference
shape used by lifecycle `bundle` members). Ordinary `JSON.stringify` is never a
protocol equality mechanism; the only retained serialization is the RFC 8785
canonical serializer, which is digest output, not an equality predicate.
Comparators read only own data properties of plain JSON objects (accessors
never invoked, inherited properties never consulted), fail closed on missing or
structurally invalid fields, and never mutate their operands.

## Relationship to WP-3

The committed WP-3 package (51 schema resources, 531 manifest entries, 114 rule
IDs, 19 digest vectors) is the normative executable specification. The schemas
and fixtures are mirrored deterministically into `src/generated/`; the
conformance runner executes the complete manifest. WP-3 documents are never
modified by this package.

## Relationship to Future Adapters

Adapters (Pi, pi-guard, MCP tools, evaluators, stores) are separate future work.
They will supply the injected interfaces and interpret validation reports; they
must never cause the core to perform hidden I/O or to treat validated output as
trusted lifecycle authority.
