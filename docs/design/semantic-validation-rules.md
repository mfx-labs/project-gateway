# Project Gateway MCP — Semantic Validation Rules

**Status:** Normative WP-3 semantic conformance catalog
**Rule-ID namespace:** `ART-*`, `TSK-*`, `AUT-*`, `CTX-*`, `CMP-*`, `BND-*`, `RES-*`, `REF-*`, `WSP-*`, `LIN-*`, `REG-*`, `LFC-*`, `EXE-*`, `PUB-*`, `MIG-*`, and `SEC-*`

## Use of This Catalog

A rule ID is a stable protocol-conformance identifier, not an implementation exception string. Every applicable rule is fail-closed. A failure must be reported using the stable failure category shown in the table and must prevent the use named by its validation phase. A validator may retain defective content for untrusted inspection or correction only.

Each table row contains the required rule fields:

- **Subject** identifies the applicable protocol subject.
- **Inputs / phase** identifies the minimum required inputs and first applicable pipeline phase from `structural-validation-profile.md`.
- **Failure** states the stable category and rejection behavior.
- **Invariant** identifies the WP-0/WP-1/WP-2 boundary preserved.
- **Fixtures** names a passing and failing normative manifest fixture. `RULE-*` fixture entries are manifest-driven coverage views of the cited base fixtures; they do not create alternative protocol content.

Rules that have an unavoidable natural-language or trusted-state boundary remain semantic even when a structural schema eliminates the most obvious forbidden field. A schema restriction is never a reason to omit the corresponding rule. Where the V1 closed schema eliminates every representable violation of a rule, the rule’s fail fixture is declared at `structural-schema-validation` (phase 4) and the rule row records that structural phase; the rule remains cataloged because the same invariant also binds cross-subject and trusted-state evaluation at its later phases. The initial V1 catalog contains 114 rule IDs.
